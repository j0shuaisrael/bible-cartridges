# Bible Cartridges — prototype (Psalm 1)

A chapter of Psalms steganographed into a PNG ("Bible cartridge"), presented
as a floating scroll in a first-person 3D scene. One isolated webapp per
chapter. This prototype is **Psalm 1 only**.

## Layout

```
index.html                  plain white "Index of /" directory listing (the hub)
decode.html                 universal decoder: drop any cartridge PNG, read the
                            chapter — nothing to install, works from file:// too
assets/
  cloud-palace.glb          the platform (sky strip surgically removed, see below)
  skybox.glb                the surrounding sky (single sphere)
psalms/encode.html          the universal encoder (one encoder for all 150
                            psalms): pick a psalm, drop your image, get the
                            cartridge — no downgrade
psalms/001/
  index.html                the Psalm 1 viewer (three.js) — THE TEMPLATE, see below
  chapter.js                chapter metadata: number, titles, filenames
  decode.js                 in-browser PSLM cartridge decoder
  encode.html               redirect → ../encode.html (the universal encoder)
  cartridge.png             the cartridge: cover + Psalm 1 text + audio, steganographed
  cover.png                 cover art (PLACEHOLDER — replace with real art)
tools/
  build_psalm001_data.py    builds psalm001_data.json (verses + lexicon) from the
                            hand-written gloss table; verifies every token
  psalm001_data.json        chapter data: 6 verses as lexicon indices + the
                            per-unique-word lexicon (Hebrew, transliteration,
                            baked gloss per language)
  built-psalms.json         the psalms actually built on disk (data + audio);
                            regenerated by build_built_psalms.py — the
                            universal encoder's picker reads this file
  build_built_psalms.py     regenerates built-psalms.json from disk
  encode.py                 builds a cartridge PNG from cover + data + audio
  decode.py                 verifies + extracts a cartridge PNG (Python)
```

## The platform GLB

`assets/cloud-palace.glb` is the Cloud Palace with its built-in sky strip
removed **properly, in the file** — not hidden at runtime. The strip was
mesh `GeometryNode_15` (84×84×42 units, 182 vertices, emissive material);
removing its node + mesh + now-unused material + orphaned accessors /
bufferViews / texture with gltf-transform shrank the file from 1,207,616 to
795,224 bytes and the bounding box from 84×84×42 to 28×28×18. The remaining
4 meshes are the real palace. `assets/skybox.glb` is the anime skybox
unchanged; the viewer measures its loaded size at runtime and scales it to
a ~60-unit radius (the file's own node matrix already makes it ~1000 units,
so a blind 60x would have made it invisible).

## The cartridge format (PSLM v3)

All lossless and exactly reversible. The decoder verifies a SHA-256 over
the text pack, over the audio, and over **each 3D model**, and returns the
exact original bytes — or reports damage.

* **Visible strip** — the top rows of the cover hold the text pack as raw
  RGB bytes (3 bytes/pixel): magic `PSLM`, version byte (`3`), a JSON
  header (chapter, packed languages, lengths, SHA-256s, strip height,
  LSB depth, the models list), then the zlib-compressed text pack. Bytes
  past the payload inside the strip are deterministic filler and are
  ignored by the decoder. The strip is at least 16 rows tall.
* **Invisible LSB layer** — ONE bitstream below the strip, at `lsb_depth`
  bits per colour channel (1 or 2, chosen as the minimum that fits),
  row-major, MSB-first within each byte. Sections in order: the Opus
  audio, then each model in header order. A channel changes by at most
  1/255 (depth 1) or 3/255 (depth 2): invisible to the eye.
* **Models** — the cartridge carries the FULL palace and skybox GLBs.
  Each model entry records its original length, its SHA-256, how many
  bytes it occupies in the LSB stream (`stored_len`), and whether those
  bytes are zlib-compressed. A model is stored compressed **only when
  that actually shrinks it** — and only losslessly, so the decoded bytes
  are byte-identical to the original GLB. Measured (2026-11-19, zlib 9):
  palace 795,224 → 291,028 (36.6%); skybox 2,697,556 → 2,622,191 (97.2%
  — its 2.58 MB is an already-compressed embedded JPEG). Draco/meshopt
  was measured and NOT adopted: it saves ~178 KB (5.7% of the payload)
  but is lossy (quantised geometry) and its decoder is a ~763 KB JS+WASM
  pair that would have to be bundled into the decoder — the decoder would
  grow by ~1 MB to save ~178 KB in the cartridge.

**Full quality is the default.** The cartridge holds the complete,
unmodified models, audio and text. Lossless zlib is the only compression
applied by default. Nothing lossy (Draco/meshopt, JPEG re-encode, lower
Opus bitrate) is ever applied without an explicit opt-in from the person
encoding.

**Capacity** (Psalm 1: audio 192,766 + palace stored 291,028 + skybox
stored 2,622,191 = 3,105,985 bytes in the LSB stream; strip 16 rows):

| cover | depth 1 | depth 2 |
|---|---|---|
| 1024×1024 | 387,072 B | 774,144 B — cannot hold the models |
| 2048×2048 | 1,560,576 B | 3,121,152 B — fits at depth 2 (99.5%, ~15 KB spare; tight) |
| 3072×3072 | 3,520,512 B — fits at depth 1 (88%) | 7,041,024 B |
| 4096×4096 | 6,266,880 B — fits at depth 1 (50%) | 12,533,760 B |

The encoder chooses the minimum depth that fits and **refuses loudly
with the numbers** when no depth fits — it never silently drops the
models, never truncates, and never falls back to fetching them.

**Small images — remote models (explicit opt-in only).** If the cover
cannot hold the models even at 2 LSBs, the encoder first refuses loudly.
The person encoding then has two explicit choices, neither automatic:
(1) turn on **"allow remote models"** (off by default): the header
records the models as remote — `{"name":"palace","remote":true,
"url":"https://j0shuaisrael.github.io/bible-cartridges/assets/cloud-palace.glb",
"len":795224,"sha256":"<hex>"}` — instead of their bytes; the decoder
fetches them ONLY when the header says remote, verifies length + SHA-256
against the header, and ALWAYS warns the cartridge is not fully offline;
(2) encode **text + audio only** (`models: []`) — the resulting cartridge
is INCOMPLETE for the world, and the decoder reports it and never fetches
models to fill the gap. Order of attempts: fit everything in the image
first (with lossless compression); offer the toggle only when the models
do not fit.

**The models never depend on the site.** The decoder builds the world
from the GLBs extracted from the image. It NEVER fetches models from the
site or from `assets/` — except a remote model, and only when the header
explicitly records it as remote. A cartridge with no models (PSLM v2, or
v3 with `models: []`) is INCOMPLETE for the world: the decoder shows its
text and audio, reports it incomplete, and never fetches models to fill
the gap. v2 cartridges still read (text + audio verify), but are
incomplete for the world.

The text pack is the chapter data JSON: verses as indices into a lexicon,
plus one entry per **unique** Hebrew word (49 for Psalm 1) — Hebrew token,
SBL-style transliteration, and a gloss in each packed language.

## Translations are baked in — no API, no cost, offline forever

The parentheticals on the scroll are `(transliteration, meaning in the
user's device language)`. The meanings are **baked into the cartridge once,
at build time** — one gloss per language per unique word, stored in the text
pack, and the cartridge header lists which languages are packed (Psalm 1:
all 12 — en, es, pt, fr, de, ru, ar, zh, hi, id, ja, ko; the human-editable
table is `tools/psalm001_meanings.csv`, one row per word, one column per
language). The decoder reads `navigator.language`, picks the best
matching packed language (`es-MX` → `es`), and falls back to English when
the device language isn't packed — and per word, when a language has no
gloss for that word, it falls back to English for that word. Hebrew +
transliteration always work regardless of language. The transliteration is
rendered in the reader's own alphabet by rule tables (Cyrillic, Arabic,
Devanagari, Hangul, katakana; Latin as stored for the rest) — rules, not
data, so nothing is fetched. Decoding never fetches anything and never costs
anything. Adding a language later means adding one gloss per word at build
time — the format needs no redesign.

## The template: one page per psalm (all 150)

`psalms/001/index.html` is the reusable template for every psalm. It holds
**nothing chapter-specific**: the chapter number, the titles shown on the
page and the scroll, and the cartridge/audio filenames all come from
`chapter.js` in the same folder; the text, transliteration, glosses and
audio all come from the cartridge itself, decoded in the browser. The 3D
world (palace, skybox, scroll, controls) is shared logic.

To make another psalm's page (e.g. Psalm 23):

1. Copy the whole `psalms/001/` folder to `psalms/023/`.
2. Replace `chapter.js` (number, title, Hebrew title).
3. Replace `cartridge.png` (built with `tools/encode.py` from that
   chapter's data + audio + cover), `cover.png`.
4. Add one line to the hub `index.html`.
5. Re-run `python3 tools/build_built_psalms.py` so the universal
   encoder's picker offers the new psalm.
6. Change nothing in `index.html` or `decode.js`.

Long chapters need a bigger cover: the LSB layer holds the audio AND the
full models (3,105,985 bytes for Psalm 1) — a 1024×1024 cover cannot hold
them at all, a 2048×2048 cover fits them at 2 LSBs (tight, ~15 KB spare),
and 3072×3072 fits them at 1 LSB. Psalm 119 (~10 min of audio, ~1.8 MB
at 24 kbps) will need a large cover too. The encoder fails loudly at
build time if a payload doesn't fit; it never silently truncates or
silently drops the models.

## Encoder + decoder pages — the "pregnant twin" maker (2026-11-20)

* **`psalms/encode.html`** — the universal encoder (the ONE encoder for
  all 150 psalms). Pick a psalm from the picker — only psalms actually
  built on disk are selectable. What counts as built is read from
  `tools/built-psalms.json` (a psalm counts as built when both its data
  file and its audio exist; regenerate it with
  `python3 tools/build_built_psalms.py` after building a psalm — one
  request, no console noise; if the manifest is missing the page falls
  back to probing for each psalm's data file, which works but logs one
  console line per psalm not built yet). The rest are shown as "not built
  yet"; `?psalm=NNN` links straight to one. Drop a PNG, JPEG, WebP, GIF,
  BMP, AVIF or HEIC image; it builds that psalm's cartridge as a
  download, in PSLM v3: text pack + audio + the full palace and skybox
  GLBs, all in the image, at the minimum LSB depth that fits (1, then 2).
  The picked psalm's chapter data is fetched from
  `tools/psalmNNN_data.json`, the audio decoded out of that psalm's own
  cartridge (`psalms/NNN/cartridge.png`), and the models from `assets/` — the same files the viewer uses, fetched
  once per page load (the same two models serve every psalm). Data and
  audio are also embedded in the page as fallbacks, but only for Psalm 1,
  used only when fetch is blocked (opening the page directly from
  `file://`) — embedding all 150 psalms would bloat the page, so the
  other psalms need the page served over HTTP. The GLBs are NOT embedded
  (3.5 MB): on `file://` the page says plainly that the models cannot be
  packed in from there and offers only the remote-models or
  text+audio-only paths — it never silently drops them. The fetched data
  is checked against the picked psalm number and refused on mismatch, so
  one psalm's chapter can never be encoded under another's number. Full
  quality is the default and is stated on the page. When the image is too
  small for the models, the page warns BEFORE encoding and offers the
  explicit opt-in **"Allow remote models"** (off by default) and a
  separate **"Encode text + audio only"** button — neither automatic.
  `psalms/001/encode.html` is now just a redirect to this page, so old
  links land on the one encoder. HEIC — the format iPhone photos use by
  default — is decoded by a bundled WASM build of libheif (libheif-js
  1.23.5, libheif 1.23.3, LGPLv3) inlined in the page as text and loaded
  only when a HEIC file is dropped: never from a CDN, never fetched at
  runtime, so the encoder stays fully portable and works from `file://`.
  The page says plainly, where a HEIC is loaded, that the decode recovers
  exactly the pixels the HEIC holds and writing them out as PNG is
  lossless (zero further loss) — and that the HEVC compression the iPhone
  already applied is lossy and cannot be undone, and that a 10-bit/HDR
  HEIC drops to 8-bit (warned when it happens). TIFF, RAW and anything
  else a browser cannot read are refused plainly ("this format can't be
  read in a browser — export it as PNG or JPEG first"), detected by magic
  bytes and by extension; the HEIC refusal with that wording is kept as
  the fallback, shown only when the bundled WASM decoder cannot start.
* **`decode.html`** (repo root) — the universal decoder, fully portable
  and fully offline (1.1 MB, three.js bundled in as base64 data: URLs —
  zero external requests, no CDN, no webfonts, no analytics). Anyone can
  drag any cartridge PNG onto it (or pick a file) and read the chapter:
  verified intercalated Hebrew + transliteration + gloss in the device
  language (English fallback, manual language picker, transliteration in
  the reader's alphabet), plus the audio player. A valid v3 cartridge
  takes over the display with the chapter's 3D world — the same floating
  scroll in the palace-and-sky world as the psalm's viewer page, built
  from the GLBs extracted from the image itself. A v2 cartridge (or a v3
  with no models) is reported INCOMPLETE: text and audio shown, no world,
  no fetch. A remote-models cartridge shows a clear "not fully offline"
  warning. On any SHA-256 mismatch it reports DAMAGE and shows nothing
  unverified. It accepts cartridges made by either the Python encoder or
  the web encoder. Its decoder is a standalone copy of
  `psalms/001/decode.js`, inlined so the page works from `file://` (a
  module import would be blocked there). The page also carries a copyable
  AI spec (a complete prompt for rebuilding an equivalent decoder from
  scratch), a "Download this decoder" button (saves the page itself, works
  from https:// and file://), and plain offline instructions (Add to Home
  on iOS/Android; opening the saved file offline on PC/Mac/Linux/Android/
  iPhone).

### The no-downgrade rule — how it is kept

* Output dimensions are exactly the input's. The art is never resized;
  the code strip is extra rows added on top.
* PNG input: the pixel data is re-encoded losslessly (filter-0 scanlines,
  zlib) and **every metadata chunk is copied verbatim** into the output
  (`tEXt`, `iTXt`, `zTXt`, `eXIf`, `iCCP`, and any others) — the file is
  never rebuilt from pixels alone. RGBA input stays RGBA; RGB stays RGB.
* JPEG input: decoded once to PNG — pixels identical to the decoded JPEG,
  never re-encoded as JPEG. EXIF → `eXIf`, XMP → `iTXt`
  "XML:com.adobe.xmp", IPTC → `zTXt` "Raw profile type iptc"
  (ImageMagick convention, hex-encoded), ICC profile → `iCCP`.
* WebP / GIF / BMP / AVIF input: decoded once to PNG — pixels identical
  to the decoded input, never re-encoded. WebP EXIF → `eXIf`, XMP →
  `iTXt` "XML:com.adobe.xmp", ICC profile → `iCCP`; AVIF EXIF / XMP /
  ICC the same way (read from the ISO-BMFF meta box); GIF comments →
  `tEXt` "Comment" and GIF XMP → `iTXt`. BMP carries no standard
  metadata — nothing to carry. Animated WebP/GIF and AVIF sequences use
  the first frame only, warned about before encoding.
* HEIC input: decoded by the bundled offline libheif WASM (see above) —
  pixels identical to the decoded HEIC, stored losslessly as PNG. EXIF →
  `eXIf`, XMP → `iTXt`, ICC → `iCCP`. The EXIF orientation is applied to
  the pixels (libheif does not do it) and the carried EXIF is patched to
  orientation 1, so no viewer rotates the image twice. Anything that
  cannot be carried is warned about before encoding, never silently
  dropped.
* The numbers are shown before encoding (pack bytes, audio bytes, model
  bytes and their stored sizes, strip rows, LSB capacity at 1 and 2 bits,
  % used, LSB depth). If the payload does not fit, the page refuses
  loudly with those numbers and disables the full-quality encode — it
  never silently truncates or silently drops the models. When the image
  is too small for the models, the page warns first and offers the
  explicit remote-models toggle (off by default) and the text+audio-only
  button. An in-page self-check re-reads the built strip and verifies
  the text pack, the audio, and every packed model SHA-256 before
  offering the download.
* Known limits: 16-bit PNG input is stored as 8-bit (the browser canvas
  holds 8-bit pixels) — the page warns when it happens. The strip filler
  bytes use a small deterministic PRNG (mulberry32) instead of Python's
  Mersenne Twister; filler is ignored by every decoder, so cartridges
  still verify — but a byte-for-byte diff against a Python-encoded
  cartridge of the same cover will differ in the filler (and in the
  compressed pack bytes, since the browser's deflate level is not
  controllable). The decoded content is identical.
* Engine quirk, measured 2026-11-20: WebKit's `CompressionStream`
  ('deflate') is non-conformant — it returns a **zlib-wrapped** stream
  instead of raw deflate. The encoder uses `'deflate-raw'` (with a
  strip-the-wrapper fallback), and the decoder's inflate retries stripped
  on failure, so both pages work in WebKit and in spec-conformant engines.

## Building a cartridge

```sh
# 1. Audio: MP3 -> Opus in WebM (plays on iPhone Safari; plain .opus/Ogg does not)
ffmpeg -i t2601.mp3 -c:a libopus -b:a 24k audio.webm

# 2. Chapter data (regenerate after editing the gloss table in
#    tools/build_psalm001_data.py)
python3 tools/build_psalm001_data.py

# 3. Cartridge: cover + text pack + audio + full models (PSLM v3).
#    The cover must be at least 3072x3072 to hold the models at 1 LSB
#    (2048x2048 fits them at 2 LSBs, tight; 1024x1024 cannot hold them
#    at all — the encoder refuses loudly). Use the COMPLETE skybox GLB.
python3 tools/encode.py --cover psalms/001/cover-test-4096.png \
    --audio psalms/001/audio.webm \
    --data tools/psalm001_data.json \
    --palace assets/cloud-palace.glb \
    --skybox assets/skybox.glb \
    --out psalms/001/cartridge.png

#    Small cover? Two explicit opt-ins, neither automatic:
#    --remote-models   (models recorded as remote URLs; world needs network)
#    --text-audio-only (cartridge incomplete for the world)

# 4. Verify (round-trip: exact bytes or DAMAGE)
python3 tools/decode.py psalms/001/cartridge.png \
    --out-text /tmp/text.json --out-audio /tmp/audio.webm
```

The encoder accepts `--audio` as optional: a cartridge without audio still
builds and decodes, with `audio_len: 0` in the header.

## Running the viewer

The viewer is an ES module and fetches its files, so serve the folder over
HTTP — opening the file directly will not work:

```sh
python3 -m http.server 8000        # from the project root
# open http://localhost:8000/  ->  white index  ->  psalms/001/
```

Controls: virtual joystick (bottom-left) or WASD to move; drag anywhere else
to look around; drag the scroll itself — or two-finger scroll / mouse wheel
over it — to read on when the text exceeds the sheet; tap/click the scroll
to play or pause the reading. `?lang=es` forces Spanish glosses;
`?scroll=0.5` starts halfway down the text.

The viewer decodes `cartridge.png` in the browser (see `decode.js`) and
renders the scroll from the decoded pack. If the cartridge is damaged it
says so on the scroll instead of failing silently. If the cartridge's
audio is missing or damaged it shows a note and the scroll still reads fine.

## Refinement round — 2026-11-19 (Pol's first look at the live site)

* **Scroll is one continuous object** — the tan sheet and the tan rolls now
  share the same height (3.5), and the sheet's edge sits inside the roll
  (roll radius 0.5, centre ±3.8, sheet plane z = −0.30), so no seam or
  see-through gap shows from any angle.
* **Trackpad scroll reads the chapter** — a wheel / two-finger scroll over
  the scroll advances the text, in addition to drag-to-scroll. Scoped to
  the scroll by raycast; a wheel anywhere else does nothing.
* **Skybox visible** — the anime sky now shows. Root cause: the sky sphere
  winds inward (signed volume < 0) and its GLB material uses
  `KHR_materials_pbrSpecularGlossiness`, unsupported in three r160, so the
  old BackSide standard material rendered nothing and the dark-navy scene
  background showed through. The sky is now an unlit `MeshBasicMaterial`
  using the decoded texture, double-sided, un-tone-mapped.

## Refinement round 2 — 2026-11-19 (the very top of the skybox)

* **Zenith black disc — fixed.** Looking straight up showed a black disc
  (~5–7° radius, serrated edge, tiny blue speck at its centre) at the top
  of the sky. Root cause, measured: the skybox GLB file itself is cut
  short — its header declares 2,697,556 bytes but the file has 2,660,849
  (36,707 bytes missing off the end) — so its embedded JPEG has no EOI
  marker and its scan data ends ~70 rows early. The sphere's zenith pole
  samples exactly those bottom rows (v near 1.0), which decode as a flat
  fill (black in the browser), hence the disc. Sketchfab displays the
  same asset fine because its pipeline fills the missing rows
  differently. The fix is viewer-side, in `psalms/001/index.html`, and
  the GLB is untouched: the viewer parses the GLB container directly
  (`parseGlbContainer`, clamping chunk lengths to the bytes present),
  decodes the sky image straight out of the BIN chunk, and rebuilds the
  sky material by hand on a pure-white base. Two things that did NOT
  work, measured: `createImageBitmap` decodes this truncated JPEG as an
  all-black bitmap (mean luminance 0.000, no error thrown), so the decode
  goes through an `<img>` element over a blob: URL instead (verified
  working here: mean luminance 0.668, only the missing rows black); and
  the stock-like emissive material also showed the disc (brown, from the
  hemisphere ground light on the backfaces), so the material swap alone
  was never the fix. The pole band is healed (`healSkyPoleBand`, adapted
  from the rainbow globe's `healPoleTexture`): the bottom 8% of rows is
  compared against a 65–80% reference band, and the contiguous uniform
  run at the bottom edge is filled by extending the first good row
  downward with a light seam blur — the log reads
  `[sky] pole check: healed 72 rows …`. If the hand-built texture fails
  for any reason, the viewer falls back to GLTFLoader's own texture with
  the same bottom-row repair (`repairSkyTexture`).
* Verified in headless WebKit (Playwright): straight-up, max-drag-up,
  and yaw-90 straight-up views all show blue sky with clouds at the
  zenith (0 near-black pixels in the old disc zone); default and outward
  views unchanged; zero console errors.
